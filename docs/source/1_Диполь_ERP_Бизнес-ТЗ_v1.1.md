# 1. Цель и границы системы

Цель — заменить распределённую модель Google Sheets единой ERP, сохранив
фактическую логику операционки, но устранив зависимость от текстовых
ключей, дублирующихся реестров, ручных «мостов», месячных листов и
скрытых формул. Система является управленческим и производственным
контуром, а не заменой бухгалтерского/налогового учёта.

- вести B2B и B2C клиентов, контактных лиц, проекты и объекты;

- принимать и импортировать заявки, сопоставлять адреса и сохранять
  связь с внешним номером;

- планировать выезды, маршруты, сотрудников, автомобили и внешнюю
  спецтехнику;

- фиксировать факт работ по SKU, объёмам, часам, фото и приёмке;

- рассчитывать ФОТ и компенсации по версионируемым правилам;

- вести материалы, номенклатуру, поступления, списания и сценарий «с
  колёс»;

- считать производственную себестоимость заявки/адреса/проекта;

- формировать акты, фотоотчёты, внутренние наряды, отчёты за период и
  сообщения;

- вести ТБ, наряды-допуски, журналы, транспорт, файловый архив, кассы и
  управленческую аналитику.

# 3. Ключевые архитектурные решения

| **Решение** | **Требование** |
|----|----|
| Проектная конфигурация | Переиспользуемый, версионируемый набор правил процесса: структура заявки, SKU, статусы, допустимые схемы и формулы ФОТ, материалы, себестоимость, документы и отчёты. Конфигурация не задаёт одну схему оплаты для всех сотрудников. |
| Конкретный проект | Отдельный экземпляр у клиента. Имеет жизненный тип «длительный/постоянный» или «разовый», сроки, документы и заявки. |
| Создание новых проектов | Уполномоченный пользователь может создать/скопировать проектную конфигурацию и новый проект без обязательной доработки кода. |
| Клиент | Самостоятельная сущность для B2B/B2C с контактными лицами, проектами, объектами и историей. |
| Адрес | Внутренний ID объекта — главный ключ; ФИАС — внешний идентификатор; поддерживаются нормализованный адрес и алиасы. |
| Заявка | Одна заявка — один адрес. Один внешний пакет может порождать несколько заявок. |
| Объект работ | Уровень опционален и включается конфигурацией. Если не нужен, допустима схема «заявка → SKU». |
| Выезд | Плановая M:N-сущность: один выезд включает много заявок, одна заявка может иметь много выездов. |
| Спецтехника | Отдельная смена/привлечение, независимое от выезда, с распределением между адресами. |
| Документы | Формируются из утверждённого факта и сохраняют версию шаблона; файл является вложением, а не источником бизнес-правил. |

| **Сущность** | **Ключевые связи и смысл** |
|----|----|
| Клиент | 1:N контактные лица; 1:N проекты; 1:N объекты/дома; документы и история. |
| Проект-конфигурация | 1:N конкретные проекты; версии правил. |
| Проект-экземпляр | N:1 клиент; N:1 конфигурация; 1:N заявки; длительный или разовый жизненный цикл. |
| МКД/объект | 1:N заявки; адрес, ФИАС, алиасы, техпаспорт, подъезды/квартиры. Может быть связан с клиентским контуром. |
| Заявка | N:1 проект; N:1 объект/адрес; 1:N объект работ/SKU; M:N выезды; документы/статусы/история. |
| Объект работ | Опциональный уровень внутри заявки: крыша, фасад, козырёк, подъезд и др. |
| SKU/услуга | Конкретное действие; объём, единица, назначенные сотрудники, факт, материалы, ФОТ. |
| Выезд | Дата, сотрудники, автомобиль, маршрут; M:N заявки. |
| Смена спецтехники | Тип, поставщик, стоимость/время; M:N адреса/заявки/проекты через распределение. |
| Материальные движения | Номенклатура → поступление → списание/возврат; назначение на работу/заявку. |
| Начисление ФОТ | Сотрудник + проект + основание + индивидуально назначенная схема/версия + сумма. Схема выбирается для сотрудника в конкретном проекте и периоде действия. |
| Документ/файл | Универсальная привязка к клиенту, проекту, дому, заявке, акту, автомобилю, ТБ и др. |
| Кассовая транзакция | Неизменяемый ID; касса/счёт, приход/расход, контрагент, проект, основание. |

| **Пример —** Например, «Скатные кровли» может быть конфигурацией, а конкретная частная кровля — разовым проектом-экземпляром на этой конфигурации. |

# 5. Клиенты и контактные лица

Система должна поддерживать юридических лиц, ИП и физических лиц в
едином реестре клиентов. Карточка клиента является точкой входа в
историю отношений, а не только набором реквизитов для документа.

| **Блок** | **Требование** |
|----|----|
| Карточка клиента | Тип, наименование/ФИО, реквизиты, телефоны/e-mail, адреса, комментарии, активность. |
| Контактные лица | Несколько контактов с должностью/ролью, каналами связи, территорией/проектом и историей активности. |
| Связи | Из карточки видны проекты, объекты/дома, заявки, документы и агрегированные показатели. |
| B2C | Повторные обращения одного человека по разным объектам сохраняются в одной истории клиента. |
| Договоры | Хранятся как документы/файлы и метаданные проекта; сами по себе не задают SKU, ФОТ или правила процесса. |

# 6. Проекты и проектные конфигурации

## 6.1. Проектная конфигурация

- набор допустимых полей заявки и обязательность полей;

- использование/неиспользование уровня «объект работ»;

- доступные SKU и единицы измерения;

- статусная схема и допустимые переходы;

- правила ФОТ, прорабских, коэффициентов, KPI и ручных корректировок;

- правила материалов: план/факт, лимиты, обязательность списания;

- правила производственной себестоимости и спецзатрат;

- формы актов, фотоотчётов, сообщений и периодных отчётов;

- требования ТБ и обязательные типы нарядов/документов.

Конфигурация создаётся/клонируется уполномоченным пользователем и
версионируется. Закрытая история не пересчитывается при изменении
конфигурации.

## 6.2. Конкретный проект

| **Поле/функция** | **Требование** |
|----|----|
| Клиент | Обязательно. |
| Конфигурация | Обязательно; фиксируется версия на момент создания. |
| Жизненный тип | Длительный/постоянный или разовый. |
| Период | Дата начала; для разового — дата/критерий завершения; для постоянного окончание может быть открытым. |
| Ответственный | Менеджер/прораб/руководитель. |
| Объекты/территория | Список объектов либо территориальная принадлежность. |
| Документы | Договоры, допсоглашения, служебные документы и разрешённые проектные исключения. |
| Статус | Активен, приостановлен, закрыт/архив; конкретный набор согласуется с жизненным типом. |

Разовый проект является полноценным проектом, а не «нестандартной
заявкой»: он должен накапливать материалы, ФОТ, спецтехнику, акты,
документы и итоговую себестоимость, после чего закрываться.

# 7. МКД/объекты и адресная модель

| **Поле/функция** | **Требование** |
|----|----|
| ID объекта | Неизменяемый системный ID — основной ключ всех связей. |
| Адрес | Нормализованное представление + исходные алиасы от внешних систем. |
| ФИАС | Хранить при наличии как дополнительный внешний ID; использовать при автоматическом сопоставлении. |
| ЖЭУ | Связь, если применимо. |
| Параметры дома | Количество подъездов, этажность, количество квартир, тип кровли, описание состояния. |
| Подъезды/квартиры | Предусмотреть структуру подъездов и матрицу/диапазоны квартир по подъездам; заявка может хранить квартиру и автоматически определять подъезд, если данные заполнены. |
| Доступы | Выход на кровлю, чердак, подвал, особенности доступа, комментарии. |
| Фото/техпаспорт | Файлы и фотографии дома, кровли, подъездов, доступов. |
| Координаты | Для карты/маршрута. |
| История | Заявки и работы формируются из связей по ID объекта, а не по текстовому адресу. |

## 7.1. Алгоритм сопоставления адресов при импорте

1.  проверить известный внешний ID/ФИАС;

2.  проверить сохранённый алиас конкретного источника;

3.  сформировать нормализованный адресный ключ и искать однозначное
    совпадение;

4.  при неоднозначности показать оператору варианты;

5.  после ручного решения сохранить новый алиас за выбранным объектом.

| **Поле** | **Требование** |
|----|----|
| Клиент | Обязательное. |
| Проект | Обязательный конкретный проект. |
| Адрес/объект | Обязательный; одна заявка — один адрес. |
| Квартира/подъезд/место | По конфигурации. |
| ЖЭУ | Если применимо. |
| Источник | Система заказчика, СУПЕР МКД+, устно, бумага, мастер, заказчик, другое. |
| Внешний номер | Единое поле номера заявки заказчика. |
| Дата заказчика | Может быть пустой. |
| Дата ERP | Обязательная системная дата создания/получения. |
| План/факт выполнения | Из планирования и факта. |
| Дата приёмки заказчиком | Отдельно от фактического выполнения. |
| Срочность | Аварийная / плановая. |
| Описание/комментарий | Проблема + внутренние комментарии и причины ожиданий. |
| Контакт | Из карточки клиента либо разовый. |
| Ответственный | Прораб/мастер/ответственный. |
| Фото | До/после и дополнительные. |

# 9. Статусная модель заявки

| **№** | **Базовый статус** | **Смысл**                      |
|-------|--------------------|--------------------------------|
| 1     | Создана            | Заявка зарегистрирована.       |
| 2     | Принята в работу   | Ответственность принята.       |
| 3     | Запланирована      | Есть план выполнения/выезд.    |
| 4     | В работе           | Начато фактическое выполнение. |
| 5     | Выполнена          | Работы физически завершены.    |
| 6     | Принята заказчиком | Факт принят заказчиком/ЖЭУ.    |
| 7     | Акт создан         | Сформирован акт.               |
| 8     | Акт подписан       | Подписанный документ получен.  |
| 9     | Отменена           | Работа отменена с причиной.    |

«Оплачена» не является базовым операционным статусом. Ожидание погоды,
аванса, материала, доступа, согласования или спецтехники фиксируется
событием/комментарием без обязательного отдельного статуса. Проектная
конфигурация может вводить дополнительные стадии, если это обосновано
процессом.

Гарантийная/повторная протечка создаётся как новая заявка с флагом и
ссылкой на исходную.

# 10. Импорт заявок из системы заказчика

- загрузка Excel-выгрузки через отдельное окно/операцию;

- сопоставление колонок с полями ERP;

- сопоставление адресов через ID/ФИАС/алиасы/нормализацию;

- предварительный просмотр новых, совпавших и спорных строк;

- создание внутренней заявки с сохранением внешнего номера и даты;

- защита от повторной загрузки одной и той же внешней заявки;

- журнал импорта с ошибками и ручными решениями.

# 11. Планирование, выезды и маршруты

Выезд — виртуальная плановая сущность на дату/временной слот. Он не
заменяет заявку и не имеет отдельного длинного производственного
статусного пути.

| **Требование** | **Описание** |
|----|----|
| M:N | Одна заявка может выполняться несколькими выездами; один выезд — несколькими заявками и адресами. |
| Сотрудники | Ответственный + произвольный состав; отдельной обязательной сущности «бригада» на старте нет. |
| Автомобиль | На выезд назначается автомобиль; конфликты занятости подсвечиваются. |
| Маршрут | Адреса заявок + промежуточные точки: склад, поставщик и т.п. |
| Представления | День, неделя, сотрудники, автомобили, адреса, карта, канбан, нераспределённые заявки. |
| Пробег | Общий пробег из карты и/или факта; распределение между заявками с ручной корректировкой и контролем суммы. |
| Перепланирование | Перенос даты/состава/автомобиля фиксируется с причиной. |

# 12. Спецтехника и специальные производственные ресурсы

ПУХТО, кран, вышка, манипулятор и аналогичные внешние ресурсы не должны
моделироваться как атрибут одного выезда. Основная сущность — отдельная
смена/привлечение спецтехники.

| **Поле/функция** | **Требование** |
|----|----|
| Тип техники | Из справочника. |
| Дата/время | Смена, интервал или фактическая длительность. |
| Поставщик | Контрагент/исполнитель услуги. |
| Стоимость | Плановая и фактическая, если требуется. |
| Ресурс | Часы, рейсы, смены или иная единица. |
| Документы | Счёт, акт, чек, накладная и др. |
| Распределение | Одна смена распределяется между несколькими адресами/заявками/проектами суммой, процентом, часами/рейсами или вручную. |
| Контроль | Показывать распределённую/нераспределённую стоимость; контролировать итог. |
| Связь с выездом | Опциональная; спецтехника существует независимо от выезда. |

# 13. Выполнение работ и мобильный кабинет

- рабочий видит задачи на сегодня и маршрут;

- может взять работу в выполнение и завершить её;

- указывает фактический объём, единицу и человеко-часы по SKU;

- загружает фото и комментарии;

- видит материалы/требования, но на старте не выполняет складское
  списание;

- видит свой рассчитанный ФОТ в разрешённой детализации;

- подтверждает наряд-допуск/инструктаж;

- может обновлять разрешённые факты карточки дома: доступы, комментарии,
  подъезды, фото, наблюдения;

- причины остановки фиксируются событием, не обязательно отдельным
  статусом.

Мастер/прораб принимает результат. Принятый факт является источником
начисления ФОТ, себестоимости и документов. Коррекция принятого факта
требует прав и аудита.

# 14. Проектные конфигурации: стартовый перечень

| **Конфигурация** | **Стартовый смысл** |
|----|----|
| Локальный ремонт АБ основной | Абонентский поток локальных ремонтов; факт работ и акты. В ФОТ доступны сменная и сдельная/KPI-схемы, назначаемые каждому сотруднику индивидуально. |
| Локальный ремонт АБ дополнительный | Та же операционная структура, но отдельная смета/отчётность. В ФОТ также доступны сменная и сдельная/KPI-схемы, назначаемые каждому сотруднику индивидуально. |
| РК-3 | Планирование крупных кровель: жалобы, дефектовка, план/факт материалов, спецзатраты, вырубка и монтаж. |
| Швы | Межпанельные швы; погонные метры, измерения, акты, ФОТ. |
| Козырьки | Очистка и ремонт с разными единицами. |
| Снег | Отдельный зимний проект. |
| Наледь | Отдельный зимний проект. |
| Демонтаж козырьков | Разовое/договорное направление. |
| Скатные кровли | Специализированные или разовые проекты. |
| B2C / частные заказы | Частные клиенты и бизнес-клиенты; как правило разовые проекты. |

Фасады не входят в обязательный стартовый набор, но архитектура
конфигураций должна позволять добавить их без создания отдельной ERP.

# 15. Локальный ремонт АБ основной / АБ дополнительный

## 15.1. Операционная логика

| **Параметр** | **Решение** |
|----|----|
| Единица заявки | Квартира, реже подъезд. |
| Несколько работ/SKU | Да, в одной заявке. |
| Ограничение 10 м² | Информационное предупреждение, без жёсткой блокировки. |
| Кто создаёт | Оператор, мастер/прораб, руководитель. |
| Выбор АБ основной/доп | В конкретном проекте/конфигурации; перенос — с аудитом. |
| Материалы | Факт по заявке; проект может иметь месячный план/лимит, но отдельная плановая спецификация каждой заявки не обязательна. |

|--------------------------------------------|--------------|
| Дефектовка                                 | шт.          |

## 15.3. ФОТ АБ

- в обеих конфигурациях — АБ основной и АБ дополнительный — должны быть
  доступны как минимум две модели оплаты: фиксированная оплата за смену
  и сдельная/KPI-оплата;

- проектная конфигурация задаёт допустимые схемы и формулы расчёта, но
  конкретная схема назначается сотруднику в рамках конкретного проекта и
  периода действия;

- в одной смене, выезде или проекте сотрудники могут рассчитываться по
  разным схемам одновременно; начисление каждого сотрудника считается
  независимо по его назначенному правилу;

- ручные премии, штрафы, авансы, корректировки и прорабские ведутся
  отдельно с основанием, автором и правилами применимости;

- изменение схемы, ставки или формулы создаёт новую версию и не
  пересчитывает закрытые начисления; отчёты по ФОТ формируются за
  произвольный период.

# 16. РК-3

- очередь домов формируется из жалоб, истории локремонтов, дефектовки,
  приоритета, бюджета и сезона;

- адреса сопоставляются по ID дома, а не по точной строке;

- подъезд может рассчитываться из матрицы квартир дома, если она
  заполнена;

- план материалов и фактические списания хранятся раздельно;

- ПУХТО, доставка, кран/вышка и иная спецтехника относятся через общий
  механизм спецзатрат/смен;

- факт вырубки и монтажа фиксируется отдельно с объёмом и
  человеко-часами;

- нормативы и пороги РК-3 не должны быть «magic numbers» в формулах —
  только версионируемые настройки.

| **P0 до разработки —** В legacy-таблице обнаружено расхождение: выплата вырубки использует p вместо рассчитанного коэффициента k; есть конфликт порога p=1,10 и базовой ставки 595/610. До реализации нужно утвердить эталон. Отдельный бриф задаёт формулу «часы × 595 × k» и диапазон 1,10 ≤ p \< 1,25 → k=1,25, но это решение должно быть подтверждено владельцем процесса. |

# 19. ФОТ, компенсации и «Мост»

## 19.1. Правила ФОТ

- проектная конфигурация/SKU задаёт допустимые типы оплаты и формулы;
  применимая схема назначается связке «сотрудник + конкретный проект +
  период действия»;

- поддерживаются человеко-часы, смена, сдельный объём, KPI/вложенная
  схема, комбинированные правила, прорабские и ручные корректировки; для
  АБ основного и АБ-доп обязательны варианты «за смену» и
  «сдельная/KPI»;

- в одном проекте разные сотрудники могут одновременно иметь разные
  схемы оплаты; одна работа/смена рассчитывается отдельно по условиям
  каждого участника;

- закрытый факт/начисление сохраняет применённую версию индивидуального
  условия оплаты и не пересчитывается при изменении тарифа или схемы;

- начисления строятся за произвольный период и расшифровываются до
  сотрудника, проекта, основания, назначенной схемы, версии правила и
  исходных данных расчёта.

## 19.2. Компенсации

| **Статус**             | **Смысл**                                 |
|------------------------|-------------------------------------------|
| Чек на руках           | Оригинал у сотрудника/мастера.            |
| Чек передан в офис     | Оригинал принят офисом.                   |
| Чек передан бухгалтеру | Передан в бухгалтерский контур.           |
| Компенсировано         | Деньги возвращены, обязательство закрыто. |

Компенсация хранит сотрудника, дату, сумму, основание, связь с
материалом при необходимости и фото/скан чека. В отчётах компенсации
отделены от ФОТ.

## 19.3. Отчёт «Мост»

ERP должна заменять ручной «Мост»: за выбранный период распределять
начисленный ФОТ на официальную и кэш-часть и разносить обе части по
проектам. Алгоритм должен быть версионируемым и раскрываемым до исходных
начислений. Точная формула остаётся отдельным бизнес-вопросом до
реализации.

# 20. Производственная себестоимость

| **Включать** | **Не включать в стартовый производственный контур** |
|----|----|
| Материалы и расходники | Налоги |
| ФОТ | Офис/административные расходы |
| Километраж/транспорт | Управленцы |
| Амортизация оборудования по нормативу | Сметчик |
| ПУХТО | Администратор |
| Доставка | Прибыль/маржа |
| Спецтехника | Бухгалтерские распределения, не являющиеся производственным фактом |
| Прочие производственные затраты из справочника |  |

Себестоимость считается на уровне заявки и агрегируется по адресу,
проекту, клиенту и периоду. Начисленные затраты не смешиваются с cash
flow.

# 21. Документы, отчётность и внутренний файлообменник

| **Документ/функция** | **Требование** |
|----|----|
| Акт выполненных работ | Проектные шаблоны; по АБ каждая заявка актируется отдельно. |
| Подписанный акт | Файл/фото/скан, связанный с актом/заявкой. |
| Фотоотчёт | Отдельный редактируемый Word-документ. |
| Периодные отчёты | По заявкам, проекту, материалам, ФОТ, компенсациям. |
| Внутренний наряд | Из планирования, заявок, работ и состава сотрудников. |
| Текстовый отчёт для чата/MAX | Автоматический, но редактируемый перед отправкой. |
| Конструктор отчётов | Фильтры: период, клиент, проект, адрес, ЖЭУ, статус, сотрудники, работы, материалы; выбор полей. |
| Форматы | Word, Excel, PDF, печать; Word/Excel — редактируемые там, где это требуется. |
| Внешний отчёт | Возможность исключить внутренние поля и служебную информацию. |

## 21.1. Файловое хранилище

Единое внутреннее хранилище должно быть доступно из карточек клиента,
проекта, объекта/дома, заявки/акта, автомобиля и ТБ. Файлы имеют тип,
дату, автора, права и при необходимости версию. Физическая реализация
хранения определяется разработчиком; бизнес-требование — единая точка
доступа из ERP и отсутствие необходимости дублировать один файл в
нескольких папках.

# 22. Техника безопасности

- отдельный раздел ТБ с приказами, журналами, инструктажами, формами и
  сканами;

- наряд-допуск на дату, объект/адрес, сотрудников и виды работ;

- шаблоны нарядов версионируются и печатаются;

- электронные журналы с фильтрами и печатью;

- работник подтверждает относящийся к нему наряд/инструктаж в мобильном
  кабинете;

- архив и роль ТБ с ограниченными правами;

- точный перечень журналов/форм утверждается со специалистом ТБ.

# 23. Автомобили и оборудование

| **Функция** | **Требование** |
|----|----|
| Карточка автомобиля | Марка, модель, госномер, закрепление, статус, пробег, комментарии. |
| Документы | Страховка, документы, ТО, ремонты, сканы. |
| Выезды | Автомобиль назначается на выезд согласно правилам планирования. |
| ТО/ремонты | Дата, пробег, стоимость, сервис/исполнитель, документы. |
| Расходы | Топливо, ремонт, ТО, детали, мойка, страховка, оснащение, прочее. |
| Пробег | Факт/расчёт маршрута и распределение между заявками. |
| Оборудование | Опциональный реестр собственного инструмента/оборудования; норматив амортизации для себестоимости. |

# 24. Управленческие финансы и кассы

Финансовый контур является управленческим. Он не заменяет бухгалтерию,
но должен связывать фактические выплаты/поступления с обязательствами и
производственными основаниями.

- единый журнал транзакций с неизменяемым UUID/номером;

- несколько касс/счетов и справочник контрагентов;

- связь платежа с проектом, сотрудником, поставщиком, компенсацией,
  начислением или иным основанием;

- начисление и фактическая выплата хранятся отдельно;

- официальный и кэш-канал доступны в отчёте «Мост»;

- правки финансовых операций аудируются;

- до миграции определить, какая часть текущей книги «Кассы» относится к
  «Диполю», а какая к межбизнесовому сервисному контуру.

# 25. Аналитика и дашборды

- операционный дашборд: новые/непланированные/просроченные заявки,
  выезды, незакрытые акты;

- план-факт ФОТ и материалов по проекту/периоду;

- приоритизация РК-3 по домам/жалобам/дефектовке;

- производственная себестоимость по заявке, адресу, проекту, клиенту;

- производительность по SKU и сотрудникам;

- качество данных: адрес без сопоставления, расход без назначения,
  незакрытый документ, нераспределённая спецтехника;

- транспорт: пробег, загрузка, ТО, расходы;

- ТБ: необработанные наряды/подтверждения и сроки документов.

# 26. Роли и права доступа

| **Роль на старте** | **Предварительные права** |
|----|----|
| Руководитель | Полный доступ, аналитика, ФОТ, кассы, проекты, справочники, документы. |
| Администратор системы | Настройка пользователей, прав, справочников, SKU, проектных конфигураций, файловых разделов. |
| Оператор | Клиенты, заявки, документы/акты, часть справочников, ввод материалов в пределах прав. |
| Прораб/мастер | Планирование, сотрудники, приёмка факта, дома, материалы/списание, документы. |
| Рабочий | Свои задачи, маршрут, объёмы, фото, комментарии, свой ФОТ, подтверждение ТБ; без списания материалов на старте. |
| Техник по безопасности | Раздел ТБ, наряды, журналы, архив. |

# 27. Аудит, версионирование и закрытые данные

- ключевые справочники, тарифы, коэффициенты, проектные конфигурации и
  шаблоны документов версионируются;

- каждое изменение критичных сущностей фиксирует пользователя, время,
  старое/новое значение;

- использованные в истории объекты не удаляются физически;

- закрытые заявки/периоды/проекты не пересчитываются задним числом при
  изменении справочника;

- коррекция закрытого факта выполняется отдельным правом и оставляет
  полный след;

- разработчик должен исключить ID, зависящие от номера строки таблицы.

# 28. Миграция и обязательные исправления legacy-логики

| **Приоритет** | **Проблема** | **Требование при миграции** |
|----|----|----|
| P0 | РК-3: формула вырубки использует p вместо k | Не переносить ошибочную формулу как эталон; реализовать только после подтверждения правила и контрольных примеров. |
| P0 | Порог p=1,10 / ставка 595 vs 610 | Утвердить и версионировать до запуска расчёта. |
| P1 | «Свод» заявок legacy неполон по месяцам | Миграцию/ETL строить по первичным данным и сверять периоды, а не копировать ограниченный формульный диапазон. |
| P1 | Адрес как текстовый ключ | После миграции все связи идут по ID объекта; старые варианты адресов становятся алиасами. |
| P1 | Статус смешан с проектом/финансовым классом | Разнести в отдельные поля/сущности. |
| P1 | Дубли швов/козырьков | Определить первичный источник и свести в один объект с разными представлениями. |
| P1 | Распределённые справочники | Собрать тарифы, работы, сотрудников, поставщиков в центральные версионируемые справочники. |
| P1 | ID кассы зависит от строки | Мигрировать на стабильный системный ID/UUID. |
| P2 | Суммирование разных единиц в снег/наледь | Хранить отдельные позиции; агрегировать только сопоставимые единицы. |
| P2 | Magic numbers и INDIRECT | Перенести параметры в конфигурации/справочники, связи — в нормальные ID. |

# 29. Нефункциональные бизнес-требования

- мобильный интерфейс рабочего должен требовать минимального числа
  действий и быть пригоден для телефона;

- поиск по адресу, номеру заявки, клиенту и проекту должен работать
  независимо от формата исходной строки;

- импорт и массовые операции должны иметь предварительный просмотр и
  отчёт об ошибках;

- все отчёты должны строиться из первичных данных, а не из вручную
  введённых итогов;

- закрытый факт и документы должны оставаться воспроизводимыми после
  обновления справочников;

- система должна поддерживать рост числа проектных конфигураций без
  создания отдельных баз/таблиц на каждую.

# 30. Открытые вопросы перед техническим проектированием

| **ID** | **Тема** | **Вопрос** |

# 32. Критерий готовности к декомпозиции разработки

ТЗ считается готовым к технической декомпозиции по конкретному модулю,
если для него определены сущности и связи, права, поля/правила, статусы,
входные/выходные документы, критерии приёмки User Stories и закрыты
относящиеся к нему P0/open questions. Технические решения (СУБД, API,
файловое хранилище, картографический сервис, стек интерфейса) выбираются
после этого и не должны менять зафиксированную бизнес-семантику.
